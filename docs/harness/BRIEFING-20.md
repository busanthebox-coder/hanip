# 3단계 브리핑 — "두께" 페이즈 (지시 20~23)

1·2단계로 콘텐츠(65과)와 앱스러움(PWA·SRS·다크·스트릭)은 끝났다. 남은 건 **학습
밀도**다. 사용자가 라이브에서 직접 짚은 문제이고, 컴파일 산출을 측정해 확정했다.

## 확정된 문제 (2026-08-03 측정, `npm run compile` 산출 기준)

1. **문법 설명 뒤에 문제가 없다.** 문법 바이트 236개 중
   - 헌트만(탭 2번 → 규칙 → 끝, 문제 0): **100개**
   - 티치만(읽기 전용, 상호작용 0): **89개**
   - 헌트+드릴(문제 1개): 47개
   → **80%가 규칙을 보여주고 끝난다.** 라이브 실측: 2과 은/는 문법 한입 완주에 15초.
2. **한입이 너무 짧다.** 619바이트 중 본편 1장이 256개(41%), 2장 이하가 366개(59%).
   중간값: 문법 1장 · 읽기 1장 · 대화 2장 (단어 6.4장 · 보스 5.5장만 정상).
3. **워밍업이 본편보다 길다.** 본편 2장 이하 366개 바이트에 복습 2장이 앞에 붙는다.
4. **어순 문제 63개 전부 이중 출제.** 대화 바이트의 order 카드가 보스 바이트에 그대로
   또 나온다(65과 중 63과에서 발생).

## 3단계 특별 규칙

A. **추가만, 변경 금지 (additive-only).** 1단계 감사 232건은 *현재 카드들*에 대한
   결론이다. 기존 카드의 내용·순서·선택지를 바꾸면 그 결론이 무효가 된다.
   허용: 바이트에 **새 카드 추가**, 중복 카드 **제거**(어순 이중 출제), 워밍업 **개수**
   조정. 금지: 기존 카드의 prompt/options/target/tokens 수정.
   → 지시 20에서 `scripts/check-additive.mjs`를 만들어 기계로 강제한다.
B. **저작 금지, 파생만.** 새 문제는 반드시 그 챕터에 이미 있는 문장·표·단어에서
   파생한다(예문 → 어순 타일, formTable 예시 → 클로즈). 새 한국어 문장을 쓰지 마라.
C. **A1 기준선은 이번엔 바뀐다.** 이 페이즈는 의도적으로 컴파일 산출을 두껍게 한다.
   재스냅샷은 **지시 23에서 단 한 번**, 그 전까지는 baseline 실패가 정상이므로
   `npm run guard`는 baseline을 건너뛴 `guard:thin`으로 돌린다(지시 20에서 추가).
   지시 23이 재스냅샷 + 이력 기록 + 게이트 원복까지 책임진다.
D. **목표 수치 (지시 23 게이트)**
   - 문법 바이트 중 문제 ≥2개인 비율 **100%** (티치 폴백 89개 포함 — 티치도 문제를 붙인다)
   - 전체 바이트 본편 카드 수 **중간값 ≥ 5**, 1장 바이트 **0개**
   - 어순 중복 **0**
   - 감사 blocker **0** (신규 생성 카드만 감사)

## 실행 순서

20(게이트·컴파일러 기반) → 21(문법 두께) → 22(대화·읽기 두께 + 중복 제거) →
23(워밍업 비율 + 재감사 + 재스냅샷 + 배포).

20이 additive 가드와 thin 게이트를 먼저 세우지 않으면 21·22에서 무엇이 깨졌는지
알 수 없다. 반드시 순서대로.
